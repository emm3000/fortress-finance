# 0005 - Sync v2: server-ordered changes with a per-user cursor

- Status: Accepted
- Date: 2026-10-05
- Supersedes: 0001 (offline-first local writes, client UUIDs, soft deletes and stable `operationId` carry over)

## Context

Sync v1 (ADR 0001) loses data. Conflicts resolve by device clock, so a skewed phone wins or loses arbitrarily, and the server trigger `set_updated_at` rewrites the timestamp the rule compares (`202603110011_h15_sync_acknowledged_operations.sql:71-76`, `202603110001_h2_baseline.sql:150,163`). Pull filters by that timestamp, so an offline insert with an old `updated_at` never reaches a device whose cursor is newer (`h15:100,138`). An ack deletes a queue row a newer edit just overwrote (`db/syncQueue.repository.ts:40-48`, `services/sync.service.ts:185`). Pull overwrites rows with pending writes (`db/transaction.repository.ts:212`). The cursor is global and survives logout (`services/sync.service.ts:152,210`, `store/auth.store.ts:64-69`). Row and queue writes are not atomic (`db/transaction.repository.ts:51-67,147,185`). Money is a float with no bounds; one `numeric(10,2)` overflow fails the whole RPC on every retry. v1 has no production data worth keeping, and the owner wants multi-device.

## Decision

**Clean cut.** Supabase and local SQLite restart from a new baseline; no data migration. The new baseline migration drops and recreates `public` (as `h2_baseline` does), contains the complete v1 schema (transactions, budget plans, day check-ins, castle state, wallet/gold, upgrades, escudos, liquidation ledger, partes, profiles with currency and timezone, push tokens, notification queue and logs) with final RLS and grants, and the superseded migration files are deleted in the same change. Liquidation logic (RPC, scheduler) lands later in phase 3 on this schema; there is no second baseline. This is the one exception to "applied migrations are immutable"; from the new baseline on, the rule holds again.

**Ordering.** Device clocks decide nothing.
- Every synced row carries a server-assigned `version` (incremented on each accepted write) and `change_seq`, taken from a per-user counter row locked inside the writing transaction. Per-user locking makes commit order equal `change_seq` order, so a pull never skips a row.
- Arrival order wins: the server applies each accepted operation in the order it receives it.
- Tombstones win: a delete sets `deleted_at` and bumps `version`/`change_seq`; an upsert arriving for a tombstoned row is rejected with reason `deleted`.
- Pull returns the user's rows with `change_seq > cursor`, in order, paged; the response carries the new cursor. The cursor is the last `change_seq` received, stored keyed by user id.
- `created_at` / `updated_at` stay as server audit columns only.

**Push and ack.**
- Each local write creates a new `operationId` (UUID v4) for its entity; the single queue row per entity is replaced, so the last payload wins locally. The `operationId` stays stable across retries of that payload.
- The server records applied `operationId`s per user and answers a replay with the original result, so a retried old operation never overwrites a newer one.
- The response lists a result per operation: `applied` (with `version`, `change_seq`) or `rejected` (with a reason code: `invalid`, `deleted`, `forbidden`). Each operation runs in its own savepoint; one bad operation never fails the batch.
- The client removes a queue row only with `WHERE operation_id = <acked id>`; if a newer write replaced it, nothing is deleted.
- A rejected operation leaves the queue as a visible rejected record (Perfil shows it with its reason) and the local row is reconciled from the server. Nothing is dropped silently.

**Local writes.** A domain write and its queue row commit in one SQLite transaction. Pull never overwrites a row with a pending operation, except a tombstone, which applies and marks that pending operation rejected (`deleted`).

**Entities in the queue.** `transaction` (client UUID v4 id), `budget_plan` (natural key `(user_id, effective_month)`; the whole plan, total plus category Límites, is one document) and `day_checkin` (natural key `(user_id, day)`). Notifications, preferences, purchases and profile stay online-only. Categories are a fixed set identified by slug; they are seeded, never synced.

**Values.**
- Money: integer minor units (`bigint` on the server, `INTEGER` locally) in the user's single currency; `0 < amount <= 100_000_000_000`, checked on client before enqueue and on server per operation. Formatting uses `Intl.NumberFormat` with the currency's ISO 4217 exponent.
- Dates: a Transaction's date is a `YYYY-MM-DD` local calendar date (`date` on the server, `TEXT` locally); a Period is its `YYYY-MM` prefix. No domain date is a timestamp.

**Local schema.** SQLite carries `PRAGMA user_version` and an ordered list of migrations run at open, each in a transaction. v1 is the baseline; on an install with `user_version = 0`, every existing table is dropped first.

**Logout** clears SQLite, the cursor, the React Query cache and unregisters the push token before the session ends.

## Alternatives considered

- **Client `updatedAt` last-write-wins with hybrid logical clocks.** Rejected: it fixes skew but keeps clock logic on every device; arrival order is enough for one user's devices.
- **Field-level merge.** Rejected: Transactions are small; whole-row replacement is predictable and testable.
- **Global Postgres sequence for `change_seq`.** Rejected: concurrent transactions can commit out of sequence order and a pull would skip rows.

## Consequences

- Two devices editing the same row offline: the later arrival wins even if it was edited earlier. Accepted.
- Every pushed operation is idempotent by `operationId`; the server keeps an applied-operations table (prunable after 30 days).
- `sync_client_state` and its client types are replaced, not extended; the invariants in `CLAUDE.md` and `.claude/rules/sync.md` change when phase 1 ships.
- Category Límites travel inside the plan document, so two devices editing different Límites of one month keep only the later plan.
